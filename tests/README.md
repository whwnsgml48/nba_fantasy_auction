# tests — validate.py 음성 테스트

`python3 tests/negative_tests.py`

이 프로젝트의 대표 실패 형태는 **「빠뜨려도 조용히 통과한다」** 이고 HANDOFF에 6건이
기록돼 있습니다. 그중 둘은 *검사 자체가 무력화된* 사고였습니다.

| 사고 | 무슨 일 |
|---|---|
| 35차 | I23이 `e["name"]`만 읽었는데 **슬롯 dict엔 `name`이 없어서** 슬롯 레벨 검사가 통째로 통과. 주입한 별칭 불일치·my_max 초과가 하나도 안 걸렸다 |
| 30차 | `has_any_basis(hits_fn=None)`이 auto basis 27건을 **영구 유효**로 만들었다 |

둘 다 "위반을 일부러 주입해 잡히는지 본다"로 즉시 드러납니다. 프로젝트 규칙에도
「새 검사를 넣으면 반드시 음성 테스트를 돌릴 것」이 있는데 **테스트 파일이 없었습니다.**

## 어떻게 동작하는가

1. `validate.py`가 읽는 파일 전체(`NEEDED`)를 **샌드박스**로 복사합니다. 원본은 건드리지
   않습니다 — `cat_model`·`divergence_rules`가 자기 `__file__` 기준으로 경로를 잡으므로
   사본이 자립합니다.
2. **무결 샌드박스가 exit 0**인지 먼저 확인합니다. 이게 깨지면 이후 결과는 전부 무의미합니다.
3. 테스트마다 위반 1건을 주입하고 **exit 1 + 의도한 마커**를 함께 요구합니다.

세 가지 함정을 구조적으로 막습니다.

| 함정 | 대응 |
|---|---|
| exit code만 보면 **다른 검사가 대신 잡아도** 통과한다 | 그 검사만 내는 마커 문자열을 요구 |
| `[I22]`·`[I23]`·`[I24]`는 **위반 0건일 때도 요약 줄에 찍힌다** | 마커를 **`✗` 줄에서만** 찾는다. 작성 당시 I22가 실제로 이 상태였고, 하네스를 하네스로 검사해서 잡았다 |
| **중단(Traceback)도 exit 1**이라 "잡았다"로 읽힌다 | **실패로 처리**한다. 추가로 `after=`로 뒤쪽 검사 실행을 직접 확인 |

## 하네스를 하네스로 검사하기

```bash
python3 tests/negative_tests.py --selftest
```

샌드박스 `validate.py`의 `err` 가산 134곳을 전부 무력화합니다. 그러면 어떤 위반도
exit 1을 내지 못하므로 **테스트가 전부 빨개져야 정상**입니다. 하나라도 초록이면
그 테스트는 검출과 무관하게 통과하고 있었다는 증거입니다. 현재 **36/36**.

중단은 검출로 세지 않습니다 — 껐는데도 exit 1이 나온 것은 검사가 살아 있어서가 아니라
검증기가 죽어서이기 때문입니다.

### 마커는 메시지 문구에 결합돼 있다

테스트가 요구하는 마커는 `validate.py`의 **출력 문장**입니다. 문구를 바꾸면 테스트가
빨개집니다 — 37차에 `피벗에 노리는 캣/포기 캣 **미명시**` → `**필드 없음**` 변경으로
`I8`이 실제로 빨개졌습니다. 이건 버그가 아니라 **설계된 결합**입니다: 검사가 사라진 것과
문구가 바뀐 것을 하네스는 구분할 수 없고, 둘 다 사람이 봐야 하는 사건입니다.
문구를 바꿀 때는 마커도 함께 갱신하고, 마커는 **안정적인 접두부**로 잡으십시오.

> ⚠️ 커버리지 표는 **손으로 유지됩니다.** 이 프로젝트에서 정적으로 적어둔 안내는 반드시
> 낡으므로, 새 불변식을 넣으면 여기와 테스트를 함께 갱신하십시오. `--selftest`는
> "있는 테스트가 살아 있는지"만 보고 **없는 테스트는 알려주지 않습니다.**

## 발견 — `validate.py`가 중단됐다 → ✅ **수정 완료 (38차)**

`I13`(앵커 슬롯의 `anchor_plan` 삭제)을 주입하면 검증기가 **`KeyError: 'anchor_plan'`**
으로 죽습니다. I13 검사 자체는 `continue`로 우아하게 넘어가는데, **툴 `CORES` 상수 대조**
구간이 `_sl["anchor_plan"]`을 직접 인덱싱합니다.
(행 번호는 적지 않습니다 — `validate.py`가 자주 바뀝니다. 하네스가 실제 행을 출력합니다.)

exit 1은 나오므로 "잡혔다"로 보이지만 실제로는 **그 지점 이후의 검사가 한 건도 실행되지
않습니다** — 툴 `P` 배열 대조(I20) · 과열 계층(I11) · 판단표(I10)가 통째로 건너뛰어집니다.
조용한 통과가 아니라 조용한 **절단**입니다.

### 고친 방법 — 한 줄로는 부족했다

`_sl.get("anchor_plan") or {}` 로만 바꾸면 **크래시 지점이 한 줄 아래로 밀립니다** —
바로 다음 줄들이 `_ap["bid_ceiling"]` · `_ap["on_fail"]["action"]` 을 직접 인덱싱하므로
빈 dict에서 다시 `KeyError`가 납니다. 그래서 블록 전체를 이렇게 바꿨습니다.

```python
_ap = _sl.get("anchor_plan")
_of = (_ap or {}).get("on_fail")
if not _ap or not _of:
    print("  ✗ 툴 CORES 대조: … anchor_plan 없음 — 상세 비교 생략(뒤쪽 검사는 계속 실행)")
    err += 1                      # ← 조용히 건너뛰지 않는다
    _cores_broken = True
    _row.append(True); _plan.append(_row); continue
```

그리고 `_cores_broken`이면 뒤의 `툴 CORES가 cores.json과 불일치 — 재생성 필요`를
**건너뜁니다.** 기대값 자체가 결손 데이터로 만들어졌으므로 그 메시지는 오진이고,
위반은 이미 위에서 가산됐으므로 중복 계상도 피합니다.

⚠️ **`.get()`으로 막을 때 조용히 넘기면 안 됩니다.** I23이 `e["name"]`만 읽어 슬롯 레벨
검사가 통째로 통과했던 것(35차)과 같은 형태가 됩니다. 방어는 하되 **위반은 남깁니다.**

### 같은 형태가 33차에 이미 터졌다

`recompute_cores`의 `if not ap: continue` 에서 **빈 dict가 falsy**라 새 앵커 2개에
`anchor_plan`이 생성되지 않았고, `sync_tool`이 `KeyError('anchor_plan')`로 죽었습니다
(`docs/04` 33차 「구현 중 걸린 것」 3번). 이번 건은 그 사고의 **하류**입니다.

### 수용 조건 3개를 테스트가 검사한다

`I13`은 이제 세 가지를 함께 요구합니다.

| 조건 | 검사 방법 |
|---|---|
| ① 크래시하지 않는다 | 출력에 `Traceback`이 없어야 한다 (**있으면 실패**) |
| ② 위반으로 잡힌다 | `✗` 줄에 `anchor_plan` 마커 |
| ③ 뒤쪽 검사가 실제로 실행된다 | `after=TAIL` — `P 배열` · `과열 임계값:` · `판단 순서:` 세 줄이 출력에 있어야 한다 |

③이 핵심입니다 — 중단도 exit 1을 내므로 **exit code와 마커만으로는 절단을 구분할 수
없습니다.** 뒤쪽 섹션이 항상 찍는 줄의 존재를 직접 확인해야 합니다.

**회귀 증명:** 수정을 일시 되돌리고 돌리면 I13이
`검증기가 **중단**됨(validate.py:867 (KeyError: 'anchor_plan'))` 으로 빨개지고,
복원하면 통과합니다. 테스트가 이 수정에 실제로 의존한다는 뜻입니다.
